# Native completion profiling

Fresh profiling after #34 identifies two separate costs in Native's one-worker echo gap: an extra failed receive to establish `WouldBlock`, and kernel completion processing during ordinary socket syscalls. Deferring io_uring task work to worker turns improves the focused throughput cases by about 6%, reducing the gap to Tokio to approximately 4–5.4% across matched runs. It also reduces measured kernel cycles per echo by 7.5%.

**This remains a prototype, not a recommendation to change the default yet.** With Aiko's normal settings, 64-byte single-connection throughput regresses by 4.2% with one worker and 10.4% with four workers in the full matrix. The ranking reverses under a temporary CPU idle-latency constraint, but that constraint also lowers absolute throughput for every backend. This demonstrates sensitivity to sleep/wakeup policy; it does not establish a specific CPU idle state or kernel defect as the cause.

## What changed

The executor still runs a ready batch and then turns its selector. Previously, fresh thread-bound rings used `COOP_TASKRUN`: Linux could process pending ring completion work on return from ordinary system calls such as `recv` and `send`. The prototype prefers `SINGLE_ISSUER | DEFER_TASKRUN | TASKRUN_FLAG`, so pending completion work is processed when the worker explicitly enters the ring. Linux also enables its lockless CQ implementation for these deferred rings. See the [setup contract](https://man7.org/linux/man-pages/man2/io_uring_setup.2.html) and [kernel ring creation](https://github.com/torvalds/linux/blob/v7.2/io_uring/io_uring.c).

The change moves kernel housekeeping to the event-loop boundary; it does not introduce another thread or change buffer ownership, socket operations, cancellation, or task migration. Nonblocking submissions explicitly request `GETEVENTS` with a zero minimum completion count. This is necessary for progress with older supported versions of the Rust io-uring library, whose `submit()` does not request `GETEVENTS` for pending task work. Timed and indefinite waits retain their existing completion collection.

Only an unused ring entering a thread-bound worker is upgraded. Rejected or unsupported deferred setup falls back to cooperative setup, then the original ring. Movable drivers and already-driven rings keep their original configuration. In the retained prototype, CQEs generated by a productive/nonblocking submission are collected on the next turn. Collecting them immediately was measured separately below.

## Why Tokio is ahead

The first [24 uninstrumented controls](results/native-profiles/baseline/aiko.json) use one worker and 32 connections:

| Backend | 64 B echoes/s | 4096 B echoes/s |
| --- | ---: | ---: |
| Tokio `AsyncRead` | 711,924 | 641,428 |
| Tokio retaining readiness until `WouldBlock` | 669,744 | 605,833 |
| Native monitor | 640,794 | 577,792 |
| Native owned receive | 626,530 | 562,924 |

Tokio's ordinary stream read clears readiness after a short positive read on Linux. In this workload, each echo is shorter than the reused 64 KiB receive buffer, so that avoids the next failed receive. The diagnostic conservative Tokio loop retains readiness until `WouldBlock`, matching Core's policy, and loses 5.9% at 64 bytes and 5.5% at 4 KiB. This comparison changes the Tokio loop; it is evidence about the policy's cost, not an exact additive decomposition of the entire Native gap. The [diagnostic benchmark patch](results/native-profiles/baseline/control.patch) records the exact loop.

Core's existing urgent-data tests demonstrate why a short read cannot universally be treated as an empty stream. This prototype preserves that behavior. Removing the extra receive safely needs an authoritative drained-stream indication, or an owned completion/receive-ahead path that can bypass speculative reads. Blindly clearing readiness after every short read would sacrifice tested behavior.

## Counters and profiles

The [matched profiles](results/native-profiles/deferred-profiles/aiko.json) contain two counter runs and one cycle profile per backend. Values below are the mean count per measured echo in the two counter runs, at one worker, 32 connections, and 64-byte payloads. Counters cover server process lifetime, including small startup/teardown costs. Tracepoints perturb execution; their throughput is not used as a capacity result.

| Backend | User cycles | Kernel cycles | User instructions | Kernel instructions | `recv` calls | Ring entries |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Native before | 942 | 8,102 | 1,537 | 16,270 | 2.00 | 0.024 |
| Native deferred | 963 | 7,498 | 1,563 | 15,900 | 2.00 | 0.067 |
| Tokio retaining readiness until `WouldBlock` | 887 | 7,656 | 1,713 | 15,928 | 2.00 | 0.000 |
| Tokio `AsyncRead` | 763 | 7,220 | 1,439 | 14,261 | 1.00 | 0.000 |

Native's userspace instruction count is already below conservative Tokio's. The deferred prototype slightly increases userspace work but removes about 604 kernel cycles per echo. Ring entry frequency increases from about 0.024 to 0.067 per echo: fewer syscalls alone is not the explanation. Batching task work and enabling the kernel's deferred-ring completion path are the useful changes here; these measurements do not separately quantify those two kernel effects.

The owned Native path has a different bottleneck. Its initial profile highlights per-operation oneshot send/receive, routing, capacity acquisition, and request lifecycle work. It executes approximately 2,867 userspace instructions per echo versus 1,537 for monitors in the initial counter runs. Reusing typed completion/request storage is a separate opportunity; this prototype does not change it. The earlier always-submit-owned-sends experiment regressed and is not repeated here.

## Testing the latency tradeoff

The tail also regresses in the full normal-policy matrix. For the single-connection, 64-byte cases, taking the median reported percentile across five runs, one-worker P99 rises from **4.283 to 9.247 µs**, while P50 falls from 3.521 to 3.411 µs. With four workers, P99 rises from **5.571 to 9.231 µs** and P50 from 3.551 to 3.991 µs. These are closed-loop client round trips, including client and kernel scheduling. The one-worker distribution is another reason not to equate lower CPU cost with uniformly lower latency.

Two follow-up code experiments were rejected:

- **Collect CQEs immediately after a nonblocking submission.** At 32 connections, this was roughly neutral for 64 bytes and 1.2% slower at 4 KiB relative to deferred processing alone. In a five-repeat single-connection comparison, it improved the one-worker median from 259,354 to 267,041 echoes/s, still below the 275,127 baseline; the four-worker median fell from 235,382 to 232,341. It did not resolve the regression. See [throughput controls](results/native-profiles/collect-comparison/aiko.json), [latency controls](results/native-profiles/latency-comparison/aiko.json), and [patch](results/native-profiles/deferred-collect.patch).
- **Keep a sole completion local without waking an idle peer.** A worker-phase flag preserved peer wakes during task polling and when local backlog existed. It produced no reliable gain over the deferred prototype and did not resolve the four-worker low-load regression, so the extra state was removed. See [controls](results/native-profiles/local-wake-comparison/aiko.json) and [patch](results/native-profiles/local-wake.patch).

The instrumented single-connection results actually favor deferred processing. Both implementations make about two receives and one ring entry per echo, with about one voluntary context switch per echo. Uninstrumented resource-usage counters also show lower server CPU cost for deferred processing, despite its higher round-trip latency. That makes it unsafe to explain the latency result solely from the instrumented profile or assume it is extra executor bookkeeping. See [single-connection profiles](results/native-profiles/latency-profiles/aiko.json).

Aiko normally uses `amd-pstate-epp`, the `powersave` governor, and `balance_performance`. Temporarily selecting the performance governor on benchmark CPUs did not resolve the ranking. Holding a zero-latency `/dev/cpu_dma_latency` request did reverse it:

| Host policy | Workers | Native before | Native deferred | Tokio |
| --- | ---: | ---: | ---: | ---: |
| Normal policy, five repeats | 1 | 275,223 | 263,707 | 276,845 |
| Normal policy, five repeats | 4 | 262,319 | 234,936 | 277,953 |
| Performance governor, three repeats | 1 | 273,335 | 266,174 | 276,195 |
| Performance governor, three repeats | 4 | 264,596 | 232,990 | 277,551 |
| Zero idle-latency QoS request, three repeats | 1 | 213,790 | 219,268 | 214,316 |
| Zero idle-latency QoS request, three repeats | 4 | 211,536 | 218,255 | 213,021 |

These are all single-connection, 64-byte controls. The frequency-policy run is [recorded here](results/native-profiles/performance-policy/aiko.json); the idle-latency run is [recorded here](results/native-profiles/idle-latency/aiko.json). The QoS request affects the machine broadly, and all three implementations were slower in absolute terms. It is a diagnostic intervention, not a recommended configuration or evidence that the normal-policy regression can be ignored. Frequency preferences were restored and the QoS file descriptor was closed after the experiments.

## Recommendation and next work

Keep this as a reviewed prototype until the normal-policy single-connection tradeoff is resolved or explicitly accepted. The busy-case improvement is reproducible, and its kernel-cycle reduction is substantial. Changing defaults on that evidence alone would hide a measured latency regression.

The next useful investigation is low-overhead timing of kernel wake-to-run and completion-delivery intervals under the normal idle policy, with separately measured controls: full tracing itself changes the ranking. In parallel with that investigation, a kernel-provided drained-stream indication could address the remaining conservative-readiness cost. TCP_INQ is one candidate to evaluate, including ancillary-data overhead, urgent data, FIN, flags, and alias behavior; it has not been implemented or benchmarked here. Reusable owned request/completion storage targets the separately profiled owned path without weakening lifetime safety.

## Reproduction and validation

The [provenance record](results/native-profiles/provenance.json) identifies every source variant and experiment. There are **345 samples: 312 uninstrumented controls, 22 counter runs, and 11 cycle profiles**. Raw counter output, self-time text profiles, patches, and all measurements are retained here; full callgraphs and binary perf recordings remain on Aiko. Empty stderr files were omitted.

Build all servers with `CARGO_PROFILE_RELEASE_DEBUG=1 cargo build --release --locked -p core-scheduler-echo-benchmark`. This is the optimized release profile with debug information, without LTO or target-CPU overrides. The machine is a Ryzen 9 9950X3D running Linux 7.2.8 and Rust 1.99.0. Servers use CPU 0 or CPUs 0–3; the unchanged four-worker client uses CPUs 4–7. These are distinct physical cores in the same L3 group. The fixed client hash is `c72f7aea7151fb83020b096cfdaccc46a70b0eeff6bbb0a0e4ea4157d1aeb071`.

All builds, controls, profiles, and tests were serialized with `/tmp/core-scheduler-perf.lock`; the [measurement scripts](results/native-profiles/scripts) acquire that lock themselves. Controls use one second of warmup and three seconds of measurement; counter runs use zero warmup and three seconds; cycle profiles use one second plus five seconds. Cases and variants are shuffled with a fixed seed. The closed-loop loopback workload uses one outstanding request per connection, TCP_NODELAY, reused 64 KiB buffers, complete partial writes, and validated payloads. It does not establish physical-network performance or server saturation.

Linux validation of the implementation passed **31,631/31,631 measured source regions**, Clippy, and documentation checks. Regression coverage includes optional setup fallback, queued I/O surviving upgrades, movable/already-driven drivers retaining their rings, and nonblocking turns making completion progress without an idle wait. Existing cancellation, migration, urgent-data, and ownership tests pass. Independent adversarial review found no substantive correctness or safety issues; the performance tradeoff is the outstanding concern.
